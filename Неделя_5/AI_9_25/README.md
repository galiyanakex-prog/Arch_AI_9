## Суть проекта

CLI-агент (RouterAI, модель `stepfun/step-3.5-flash`) с **явной моделью памяти**,
**настраиваемой персонализацией**, **формализованным состоянием задачи**, **набором
неизменяемых правил (инвариантов)**, **контролируемым жизненным циклом задачи**,
**подключением к внешнему миру через MCP** (внешний источник инструментов) и —
главное для Дня 25 — **production-like мини-чатом**: история диалога + RAG на каждый
вопрос + источники в каждом ответе + **память задачи**.

RAG (Retrieval-Augmented Generation) — паттерн дополнения ответа LLM **нашими**
знаниями прямо во время инференса. День 25 доводит RAG до **диалогового продукта**:
мини-чат ведёт **историю сообщений**, на **каждый** новый вопрос ищет контекст в базе
(поиск → реранкинг → фильтрация → цитаты), **отвечает с учётом найденного** и
**всегда выводит источники** (`source` + `section/chunk_id`). Поверх — **память задачи
(task state)**: что пользователь уточнил, какие ограничения/термины зафиксированы, в
чём **цель диалога** — чтобы в длинном диалоге ассистент **не терял цель**.

Центральный цикл мини-чата после переработки под День 25:

```
loop:
  сообщение пользователя
    → история диалога:  remember_message("user")          # 1) хранит историю
    → память задачи:    обновить уточнения/термины/цель    # task state
    → RAG:              retrieve(вопрос ⊕ цель ⊕ термины)  # 2) поиск контекста
                        → реранкинг → фильтр → top-K
    → ответ:            llm.complete(история ⊕ [rag])      # 3) с учётом найденного
    → источники:        sources[] + цитаты                 # 4) ВСЕГДА
    → история:          remember_message("assistant")
```

Пайплайн строкой (как в постановке дня): **история диалога → RAG на каждый вопрос →
ответ с учётом найденного → источники всегда**, плюс **память задачи**.

Ключевые границы:

- **RAG на каждом вопросе**: не однократный поиск, а поиск в каждом обмене, с учётом
  истории и цели диалога.
- **Источники всегда**: без источников ответ не выдаётся (как в Дне 24); при слабом
  контексте — «не знаю» + уточнение.
- **Память задачи — не диалог**: `task_state`/`working_memory` — пересчитываемое
  состояние (уточнения, термины, цель), отдельно от append-only истории сообщений.
- **RAG ≠ переход**: `TaskStage` не меняется ни от поиска, ни от источников, ни от
  уточнений; RAG-стадий нет.
- **`rag/` и `core/` не импортируют друг друга** — связь только через DI-фасад
  `RagService` и готовый текст блока `[rag]`.
- **RAG выключен по умолчанию**: без флага промпт байт-в-байт прежний, `rag` не
  импортируется. Прежние тесты и критерии приёмки проходят без RAG и без сети.
- **Локальность и приватность**: эмбеддинги считаются локально (Ollama, HTTP на
  `127.0.0.1:11434`); приватные данные не покидают машину.
- **MCP выключен по умолчанию** (`mcp_enabled=False`); без флагов агент работает ровно
  как раньше.

### Четыре требования к мини-чату

```python
class MiniChat:
    def __init__(self, user_id, rag_enabled=True):
        self.history: list[Message] = []          # 1) история диалога
        self.task_state: TaskState                # память задачи (усиление)
        self.rag = RagService(...) if rag_enabled else None

    def ask(self, question: str) -> ChatAnswer:
        self.history.append(Message("user", question))         # хранит историю
        self.task_state.update(question)                       # память задачи: уточнения/термины/цель
        query = self.task_state.enrich(question)               # вопрос ⊕ цель ⊕ термины
        hits = self.rag.search(query) if self.rag else []       # 2) RAG на каждом вопросе
        if self.rag and self.rag.is_weak(hits):
            return ChatAnswer(text="Не знаю. Уточните вопрос.", sources=[], ...)
        answer = self.llm.complete(self.build_prompt(self.history, hits))  # 3) с учётом найденного
        self.history.append(Message("assistant", answer.text))
        return ChatAnswer(text=answer.text, sources=answer.sources,   # 4) источники ВСЕГДА
                          quotes=answer.quotes, task_state=self.task_state.snapshot())
```

### Усиление: память задачи (task state)

Три обязательных поля памяти задачи:

- **что пользователь уже уточнил** — список уточнений (append-only по мере диалога);
- **какие ограничения/термины зафиксированы** — `constraints[]` и `terms{}` (глоссарий
  диалога);
- **что является целью диалога** — `goal` (формулируется и уточняется по ходу).

### Проверка: 2 длинных сценария

- **2 сценария по 10–15 сообщений** каждый;
- критерии: ассистент **не теряет цель** (goal сохраняется и учитывается), **продолжает
  выдавать ответы с источниками** (источники в каждом ответе).

## Мини-чат (CLI)

### Что делает мини-чат

Production-like CLI-чат поверх существующего агента:

1. **Хранит историю диалога** — неизменяемые сообщения (`ShortTermMemory`, scope=`session`)
   с `id`/`parent_id`, append-only;
2. **Ищет контекст в базе при каждом новом вопросе** — `RagService.search` (кэш →
   BM25⊕dense → RRF → реранк → фильтр → top-K) на **каждом** обмене, а не один раз;
3. **Отвечает с учётом найденной информации** — блок `[rag]` подмешивается в промт
   (после `[tools]`, до `[long_term]`), LLM отвечает **только по источникам**;
4. **Всегда выводит источники** — `sources[]` (`source` + `section/chunk_id` + `score` +
   `[doc_id#chunk_id]`) + **цитаты** (дословные фрагменты чанков).

### Учёт истории и цели при поиске

Запрос для RAG обогащается контекстом диалога, чтобы не терять нить:

- **query enrichment**: к вопросу добавляются `goal` и зафиксированные `terms`
  (из памяти задачи) — поиск находит релевантное даже для коротких уточнений («а как
  это работает?»);
- **история в промт**: `short_term` (окно 10) идёт отдельными сообщениями — LLM видит
  диалог;
- **query rewrite** (опц.): переформулирование с учётом истории (llm/heuristic).

### Формат ответа мини-чата

```
Вы: как запретить агенту менять технологический стек проекта?

AI_9:
  Изменение технологического стека запрещено инвариантом: перед выполнением
  действия запускается отдельная Python-проверка, и при нарушении инструмент
  не вызывается — выдаётся отказ с правилом и альтернативой.

Источники:
  1. [5a49d570#0] core/invariants.py · раздел: «Инварианты» · score=0.62
  2. [5a49d570#7] README.md · раздел: «Инварианты и ограничения состояния» · score=0.58

Цитаты:
  1. [5a49d570#0] «…перед выполнением действия запускается отдельная Python-проверка…»

Память задачи: цель — «понять механизм инвариантов»; термины: инвариант, ProposedAction
```

## Память задачи (task state)

**Память задачи** — пересчитываемое состояние диалога, отдельное от истории сообщений.
Хранится в `working_memory.json` (scope=`task`) и/или `task_state.json`.

### Структура памяти задачи

```python
@dataclass
class TaskState:
    goal: str                       # цель диалога (формулируется/уточняется)
    clarifications: list[str]       # что пользователь уже уточнил (append-only)
    constraints: list[str]          # зафиксированные ограничения
    terms: dict[str, str]           # зафиксированные термины/глоссарий диалога
    open_questions: list[str]       # открытые вопросы (задел)
```

| Поле | Что хранит | Пример |
|---|---|---|
| **`goal`** | цель диалога | «разобраться, как работает память задачи» |
| **`clarifications[]`** | что пользователь уточнил | «речь про RAG, не про MCP» |
| **`constraints[]`** | зафиксированные ограничения | «только локальные эмбеддинги» |
| **`terms{}`** | термины/глоссарий | `{"task state": "пересчитываемое состояние задачи"}` |
| **`open_questions[]`** | открытые вопросы | «нужен ли VPS?» |

### Как обновляется

- **детерминированно** (без LLM): по триггерам-фразам («цель: …», «уточняю: …»,
  «ограничение: …», «термин X — это …») обновляются соответствующие поля;
- **опционально через LLM**: краткое извлечение цели/терминов из сообщения (фолбэк —
  детерминированная эвристика);
- **merge, не перезапись**: `clarifications`/`constraints` дополняются, `terms`
  мержатся по ключам, `goal` уточняется (последняя явная формулировка);
- **в промт** память задачи входит блоком `[working]` (и/или отдельным блоком «Цель и
  термины»), участвует в дозированной доставке.

### Зачем нужна

В **длинном диалоге** (10–15 сообщений) без памяти задачи ассистент «теряет цель»:
отвечает на последнее уточнение в отрыве от контекста. Память задачи:

- **держит цель** (`goal`) — поиск и промт всегда учитывают её;
- **фиксирует термины** — короткие уточнения ищутся с их учётом;
- **сохраняет ограничения** — ответы не противоречат ранее сказанному.

## Модель памяти

| Тип | Что хранит | Где (файл/хранилище) | Почему так |
|---|---|---|---|
| **Краткосрочная** (`ShortTermMemory`, scope=`session`) | **история диалога** — неизменяемые сообщения с `id`/`parent_id` | `users/<id>/tasks/<task>/sessions/<sid>/session.json` | сообщения — история (append-only); `parent_id` — задел ветвления |
| **Рабочая** (`WorkingMemory`, scope=`task`) | **память задачи**: `description`, `goal`, `clarifications`, `constraints`, `terms`, `refs`, `decisions`, `facts`, `open_questions`, `current_state` | `users/<id>/tasks/<task>/working_memory.json` | **пересчитываемое состояние**, а не лог сообщений |
| **Долговременная** (`LongTermMemory`, scope=`user`) | `profile_ref` (ССЫЛКА), `tasks[]`, `decisions[]`, `knowledge[]` | `users/<id>/long_term_memory.json` | живёт между сессиями; профиль — отдельно, здесь ссылка |
| **Профиль** (`Profile`, scope=`user`) | несколько профилей: `profile_id`, `name`, `domain`, `triggers[]`, `style` + `constraints` + `context`, `skills[]` | JSON в SQLite (`profiles(user_id, profile_id)`), зеркала `users/<id>/profiles/<pid>.json` | отдельная сущность в БД; запись слиянием (MERGE) |

**История диалога** — это `ShortTermMemory`; **память задачи** — это `WorkingMemory`
(+ снимок в `task_state.json`). Разные сущности, разные файлы.

Единая точка входа — `MemoryManager`: `remember()` / `recall()` / `build_blocks()`
(порядок `LAYER_ORDER = profile → long_term → working → short_term`) / `report()`.

### Иерархия хранения

```
users/<user_id>/
├── profile.json                 # зеркало профиля default (авторитет — SQLite profiles)
├── profiles/                    # зеркала всех профилей пользователя
├── long_term_memory.json        # profile_ref + задачи + решения + знания
├── integrations/mcp/            # ветка MCP (servers.json + catalog.json + scheduler/)
└── tasks/<task_name>/
    ├── invariants.json          # ConstraintSet (неизменяемые правила задачи)
    ├── task_state.json          # снимок TaskState (+ transition_log + память задачи)
    ├── working_memory.json      # ПАМЯТЬ ЗАДАЧИ: goal/clarifications/constraints/terms
    ├── sessions_resume.md       # резюме сессий задачи (блок summary)
    ├── tool_audit.jsonl         # история вызовов инструментов (task-scope)
    └── sessions/<session_id>/   # session_id = ГГГГММДД_ЧЧММСС
        └── session.json         # ИСТОРИЯ ДИАЛОГА: сообщения с parent_id
```

Разные сущности — разные файлы. **Очистка истории диалога не сбрасывает память задачи,
не удаляет инварианты и не трогает журнал переходов.** Все пути знает только
`storage/store.py`; битый или отсутствующий файл не роняет приложение.

### Сборка промта (явные блоки + дозированная доставка + бюджет)

```
[system: роль] → [system: profile] → [system: invariants] → [system: tools, опц.] →
[system: rag, опц.] → [system: long_term] → [system: working (память задачи)] →
[system: summary, опц.] → [messages: short_term (история, окно 10)] →
[user: текущий запрос] → [резерв под ответ]
```

- `BLOCK_ORDER` = `role, profile, invariants, tools, rag, long_term, working, summary,
  short_term, current`; блок `[rag]` идёт **после `[tools]`, до `[long_term]`**;
- блок `[working]` содержит **память задачи** (цель, уточнения, ограничения, термины);
- блок `[rag]` содержит найденные чанки со ссылками `[doc_id#chunk_id]`, метаданными
  (`source`/`section`) и инструкцией-контрактом (отвечать только по источникам, приводить
  цитаты, указывать ссылки);
- `short_term` (история диалога) идёт отдельными сообщениями, окно 10;
- бюджет: необязательный блок пропускается, если `used + tokens > budget`; блок `[rag]`
  усекается **первым**; роль и запрос не урезаются никогда.

## Персонализация

Поверх памяти — **несколько профилей на пользователя** (`profile_id`, `name`, `domain`,
`triggers[]`, `style`, `constraints`, `context`, `skills[]`). Активный профиль привязан
к сессии и входит в каждый промт.

- **хранение**: SQLite + зеркала `users/<id>/profiles/<pid>.json`; **запись слиянием**
  (MERGE);
- **память независима от профилей** — переключение профиля не трогает слои памяти;
- **профиль RAG/MCP менять не может** — только явная механика профилей.

**Профиль-роутер** (`core/profile_router.py`) выбирает профиль по тексту запроса
детерминированно, без LLM: **+2** за триггер, **+1** за `domain`; победитель = максимум
(>0); ничья/ноль → `None`. Режим `/profile auto on` запускает роутер на каждый запрос
**до** сборки промта.

## Инварианты и ограничения состояния

Слой **неизменяемых правил**: **инвариант — условие, которое должно сохраняться во всех
допустимых состояниях**. Перед действием запускается **отдельная Python-проверка**
(«код запрещает, промт рекомендует»).

| Сущность | Назначение |
|---|---|
| `Invariant` | правило: `id`, `description`, `category`, `severity`, `active` |
| `ConstraintSet` | набор правил — **отдельная сущность** |
| `ProposedAction` | действие (`technology`, `adds_dependency`, `changes_database_schema`, `language`; + MCP-поля) |
| `InvariantChecker` (ABC) | `check()` (блокирующие) + `warnings()` |
| `RuleBasedChecker` | детерминированная реализация без LLM |
| `update_invariant` | изменение — только авторизованной операцией (`authorized=True`) |

Хранение — `users/<id>/tasks/<task>/invariants.json`, отдельно от диалога. При нарушении
инструмент **не вызывается**, выдаётся отказ с 4 частями. Правило `tool.deny.<qualified>`
запрещает конкретный инструмент. **Переходы и инварианты — разные сущности контроля.**

## Контролируемые переходы состояний

**Жизненный цикл задачи — строгая машина состояний**: запрет «перепрыгнуть» этап
работает на уровне кода.

### Модель состояний (`TaskStage` — 8)

```python
class TaskStage(Enum):
    NEW = "new"
    PLANNING = "planning"
    PLAN_APPROVED = "plan_approved"
    IMPLEMENTATION = "implementation"
    VALIDATION = "validation"
    DONE = "done"
    PAUSED = "paused"
    FAILED = "failed"
```

### Карта переходов (whitelist)

```python
ALLOWED_TRANSITIONS = {
    NEW:            {PLANNING, PAUSED, FAILED},
    PLANNING:       {PLAN_APPROVED, PAUSED, FAILED},            # НЕТ implementation
    PLAN_APPROVED:  {IMPLEMENTATION, PLANNING, PAUSED, FAILED},
    IMPLEMENTATION: {VALIDATION, PLANNING, PAUSED, FAILED},
    VALIDATION:     {DONE, IMPLEMENTATION, PLANNING, PAUSED, FAILED},
    PAUSED:         set(),        # выход только через resume_task() → previous_stage
    DONE:           set(),        # терминальная
    FAILED:         {PLANNING},   # восстановление — явный /task retry
}
```

Запреты реализуются **отсутствием дуги** (не `if`-ами). **История, RAG, источники и
память задачи машину не трогают**: RAG-стадий нет; уточнения/термины не меняют `TaskStage`.

### Цикл мини-чата

```
индексация (офлайн):
  corpus.list → chunking (overlap) → embedding (Ollama) → index (BM25 + vectors, норм. 0..1)

мини-чат (онлайн, каждый вопрос):
  сообщение → история (session.json, append-only)
    → память задачи: goal / clarifications / constraints / terms (merge)
      → query = вопрос ⊕ goal ⊕ terms
        → RAG: BM25⊕dense → RRF → реранк → фильтр → top-K
          → max(score) < threshold ?  да → «Не знаю. Уточните вопрос.»
          → context_block [rag] (источники + цитаты + инструкция-контракт)
            → промт: [working (память задачи)] ⊕ [rag] ⊕ [short_term (история)]
              → LLM → ОТВЕТ
                → sources[] (source + section/chunk_id)  ← ВСЕГДА
                → quotes[]  (дословные фрагменты)
                  → grounding: смысл ⊆ цитаты → ok | partial | hallucination
                    → история (append assistant) → след. вопрос
```

### Хранение истории и памяти задачи

- **История диалога** — `session.json`: неизменяемые сообщения с `id`/`parent_id`
  (append-only), окно 10 в промте; переживает перезапуск.
- **Память задачи** — `working_memory.json` (+ снимок в `task_state.json`): `goal`,
  `clarifications[]`, `constraints[]`, `terms{}`, `open_questions[]`; обновляется
  merge-ом, участвует в поиске (enrichment) и промте (блок `[working]`).
- **Разделение**: очистка истории диалога **не** сбрасывает память задачи; сброс памяти
  задачи **не** удаляет историю.

### Источники всегда

- Каждый ответ мини-чата содержит `sources[]` (`source` + `section/chunk_id` + `score` +
  `[doc_id#chunk_id]`) и `quotes[]`;
- Без источников ответ не выдаётся (проверяется `verify.py`); при слабом контексте —
  «не знаю» + уточнение;
- **RAG на каждом вопросе**: поиск выполняется в **каждом** обмене, а не однократно.

### Три кратких описания архитектуры

#### Формула для самой краткой характеристики (1 строка)

> AI_9 — production-like **мини-чат (CLI)** на базе персонализированного stateful-агента,
> который **хранит историю диалога**, при **каждом** новом вопросе ищет контекст в базе
> через RAG, **отвечает с учётом найденного** и **всегда выводит источники**, а **память
> задачи** (цель / уточнения / термины / ограничения) не даёт потерять нить в длинном
> диалоге.

#### Краткое и точное описание (одно предложение)

> AI_9 — CLI stateful-агент (RouterAI, step-3.5-flash), доведённый до **production-like
> мини-чата**: история диалога хранится в краткосрочной памяти (`session.json`,
> append-only, окно 10), при **каждом** вопросе выполняется RAG-поиск (BM25⊕dense → RRF →
> реранкинг → фильтр по порогу → top-K, локальные эмбеддинги Ollama), ответ строится
> **с учётом найденного** и **всегда** сопровождается **источниками** (`source` +
> `section/chunk_id` + `[doc_id#chunk_id]`) и **цитатами**, а **память задачи**
> (`task state`: цель диалога, что уточнил пользователь, зафиксированные термины и
> ограничения) удерживает контекст — проверено на **2 длинных сценариях по 10–15
> сообщений**; при слабом контексте — «не знаю» и просьба уточнить.

#### Полная картина архитектуры с механикой частей

Общая формула: пять основ (память → персонализация → состояние → инварианты →
контролируемый жизненный цикл) + MCP как внешний источник инструментов + **RAG-модуль**,
собранные в **production-like мини-чат** Дня 25: диалог + RAG на каждый вопрос +
источники всегда + память задачи.

1. **Хранилище (storage/)** — «где всё лежит»: иерархия `users/<id>/…`, ветка MCP,
   индекс RAG (`rag/index/`, `.gitignore`), `session.json` (история диалога),
   `working_memory.json`/`task_state.json` (память задачи). Битый/отсутствующий файл →
   схема по умолчанию, не падение. Вся запись — через фасад `Store`.

2. **Память (memory/)** — «что агент помнит»: **история диалога** (`ShortTermMemory`,
   append-only) + **память задачи** (`WorkingMemory`: goal/clarifications/constraints/
   terms) + долговременная + профиль; MERGE/append только через MemoryManager,
   дозированная доставка + токен-бюджет.

3. **Ядро (core/)** — «кто решает»: **`chat.py`** (цикл мини-чата: история → RAG →
   ответ → источники), **`task_state.py`** (память задачи: обновление и enrichment
   запроса), прежние сущности + инструменты + RAG-мост (`prompt_builder.py`,
   `agent.py`).

4. **Интеграции (integrations/)** — «как достучаться до внешнего мира»: `mcp/` и
   `scheduler/`; SDK — только здесь.

5. **RAG (rag/)** — «что агент знает из документов»: индексация (`corpus` → `chunking`
   с overlap → `embedding` → `index`); поиск (`retrieval` → RRF → top-K_before); второй
   этап (`rerank` + фильтр по порогу → top-K_after); `sources.py`/`citations.py`
   (источники + цитаты); `grounding.py` (сверка + `insufficient` → «не знаю»);
   `verify`/`eval`/`compare`. Сеть — только `127.0.0.1:11434`. Связь с ядром — DI.

6. **Оркестратор и CLI** — «как этим пользуются»: **мини-чат** (REPL/one-shot) отвечает
   с блоком `[rag]` и памятью задачи; `build_agent()` при `--rag` собирает `RagService`;
   команды `/chat …`, `/rag …`, `/mcp …`; флаги `--chat`, `--chat-scenarios`,
   `--rag`, `--rag-threshold`. Жизненный цикл (`/plan → /approve → /step|/run →
   validation → done`) не изменён.

7. **Служебное пространство (dev/)** — «проект про проект»: план-эталон → рабочие планы
   → журнал; тестовый контур L1–L4 + гейт; приёмка; сценарии длинного диалога;
   транскрипты живых прогонов.

**Инвариант всей системы**: детерминизм недетерминированной LLM даёт код; RAG/MCP —
адаптеры, которые не имеют права менять внутреннее состояние агента; **ответ без
источника — не ответ**.

## Агентный цикл

```
старт → DI-сборка build_agent(rag_enabled=--rag, mcp_enabled=--mcp) → идентификация user_id
      → активный профиль (--profile) → deliver (--deliver ∩ DELIVERABLE)
мини-чат (на каждое сообщение):
  сообщение → история диалога (append-only, session.json)
           → память задачи: goal / clarifications / constraints / terms (merge)
           → query = вопрос ⊕ goal ⊕ terms
           → RagService.search (кэш → BM25⊕dense → RRF → реранк → фильтр → top-K)
           → max(score) < threshold ?  да → «Не знаю. Уточните вопрос.»
           → context_block [rag] (источники + цитаты + инструкция «только по источникам»)
           → промт: [working (память задачи)] ⊕ [rag] ⊕ [short_term (история)]
           → llm.complete → ОТВЕТ + sources[] + quotes[]
           → grounding: смысл ⊆ цитаты → ok | partial | hallucination
           → история (append assistant) → след. сообщение
автомат: /plan → /approve → /step|/run → validation → done|failed (RAG не меняет переходы)
выход:  save_state() + сейв task_state.json (история + память задачи + transition_log)
```

LLM за интерфейсом: `LLMClient (ABC)` → `RouterAIClient` (живой: POST + Bearer, retry на
HTTP 429, таймаут 30 сек, сбой → `None`) и `MockClient`.

## Порядок достижения итогового состояния

Порядок по зависимостям:

1. **Базовый агент** — память, профили, инварианты, машина состояний, LLM-клиент.
2. **MCP-слой** — контракты инструментов → реестр → `integrations/mcp/` → policy/executor
   → LLM tool-use → CLI (наследие).
3. **RAG-индексация** — `config` → `corpus` → `chunking` (**overlap**) → `embedding`
   (Ollama) → `index` (нормализация 0..1).
4. **RAG-поиск и второй этап** — `retrieval` (bm25|dense|hybrid → RRF) → `rerank` →
   фильтр по порогу → `rewrite`; `sources`/`citations`/`grounding`/`verify`.
5. **История диалога** — `session.json` (append-only, окно 10) через `MemoryManager`.
6. **Память задачи** — `core/task_state.py` (goal/clarifications/constraints/terms) →
   enrichment запроса → блок `[working]`.
7. **Мини-чат** — `core/chat.py` (история → RAG на каждый вопрос → ответ → источники) →
   CLI (`--chat`, `/chat …`).
8. **Сценарии** — 2 длинных сценария по 10–15 сообщений + автопрогон
   (`--chat-scenarios`), проверка «цель не потеряна, источники в каждом ответе».
9. **Финал** — прогон L1→L4 + гейт, сценарии, живой прогон (Ollama + LLM), запись итога
   в `dev/migr_log.md`, предложение коммита (коммит — только по явной команде).

## Риски и откат

- **Регрессия базового агента** — RAG/чат выключены по умолчанию (`--rag`/`--chat`): без
  флага поведение прежнее, `rag` не импортируется. Откат — не включать флаги.
- **Зависимость от Ollama** — при недоступности `127.0.0.1:11434` деградация на
  `HashingEmbedder`; юниты и гейт от Ollama не зависят. Откат — не использовать `--rag`.
- **Потеря цели в длинном диалоге** — лечится памятью задачи (`goal` учитывается в поиске
  и промте); проверяется на 2 сценариях.
- **Ответ без источника** — недопустим: `verify.py` фиксирует ответы без источников;
  в `strict` — одна авто-перегенерация.
- **Рост истории** — окно 10 в промте + резюме сессий (`sessions_resume.md`); полная
  история остаётся в `session.json`.
- **Галлюцинация** — три уровня: порог релевантности → обязательные цитаты → grounding.
- **Приватность** — эмбеддинги и сверка считаются локально.
- **Загрязнение рабочих данных** — тесты пишут только в `dev/tests_debug/.tmp/`.

## Известные шероховатости и заделы

- **Формат сдачи Дня 25 — код**; точные имена файлов отчёта в постановке не названы.
- Модель эмбеддингов конфигурируема (`bge-m3` по умолчанию, `nomic-embed-text` по лекции).
- Обновление памяти задачи — детерминированно по триггерам-фразам; LLM-извлечение
  цели/терминов — опционально (фолбэк — эвристика).
- Реранкинг — интерфейс под cross-encoder с детерминированным офлайн-фолбэком
  (`LexicalReranker`); живой cross-encoder подключается при наличии.
- Задел: ветвление диалога (`parent_id`), долговременная память фактов из диалога,
  «подсветка» цитат в источнике, мультимодальный RAG, кэширование реранк-оценок.
- `transition_log` растёт без ограничения (сжатие — задел).
- Изменения не закоммичены (коммит — только по явной команде пользователя).

## Результат

- **Мини-чат (CLI) реализован**: хранит **историю диалога** (`session.json`, append-only),
  при **каждом** новом вопросе ищет контекст в базе через **RAG**, **отвечает с учётом
  найденного** и **всегда выводит источники**.
- **Источники всегда**: каждый ответ содержит `sources[]` (`source` + `section/chunk_id` +
  `score` + `[doc_id#chunk_id]`) и **цитаты** (дословные фрагменты чанков).
- **Память задачи (task state)**: что пользователь уточнил (`clarifications[]`), какие
  ограничения/термины зафиксированы (`constraints[]`, `terms{}`), что является целью
  диалога (`goal`); учитывается в поиске (enrichment) и промте (блок `[working]`).
- **Проверка на 2 длинных сценариях** по 10–15 сообщений: ассистент **не теряет цель** и
  **продолжает выдавать ответы с источниками** (`./run.sh --chat-scenarios`).
- **Режим «не знаю»** (из Дня 24): при релевантности ниже порога — «не знаю» + просьба
  уточнить, без вызова LLM.
- **Анти-галлюцинации**: порог релевантности → обязательные цитаты → grounding
  (`ok|partial|hallucination|insufficient`).
- **Техника RAG**: чанкинг с **overlap**, нормализация векторов `0..1`, косинусное
  сходство, bi-encoder top-K_before → второй этап (реранкинг + фильтр) → top-K_after.
- **Локальность и приватность**: эмбеддинги и сверка — локально (Ollama, `127.0.0.1:11434`).
- **Без регрессии**: RAG/чат выключены по умолчанию; базовый агент, MCP-слой и машина
  состояний не тронуты; «RAG ≠ переход» (`TaskStage` не меняется).
- **Проверяемость**: L1–L4 и гейт — без живого ключа и сети; живой прогон (Ollama +
  реальный LLM) — отдельно.
